Bab 1 — Kejelasan tentang CR Ini
Apa yang Mau Diselesaikan
Proses rekonsiliasi oleh tim Operation untuk transaksi QRIS (Acquirer & Issuer) di Paydia saat ini masih sebagian besar manual — menggunakan Excel untuk review hasil rekon dan Microsoft Sharepoint untuk pencatatan dispute. Ini tidak scalable, rawan human error, dan berisiko miss SLA settlement seiring pertumbuhan volume transaksi.
Kondisi Sistem Saat Ini
Engine rekonsiliasi sudah berjalan — proses matching Acquirer dan Issuer sudah ada, hasil match dan unmatch sudah dihasilkan oleh sistem IT. Masalahnya adalah tim Ops harus membuka dan menganalisis file CSV secara manual setiap hari untuk melihat hasil tersebut. Belum ada interface yang memungkinkan Ops bekerja langsung dari sistem.
Solusi yang Dibangun
Interface rekonsiliasi yang menampilkan hasil dari engine existing — tabel Match dan Unmatch untuk Acquirer dan Issuer — lengkap dengan fitur flagging, input dispute, re-run matching, approval settlement, dan export. Tidak ada perubahan pada engine matching yang sudah berjalan.
Flow Besar yang Disepakati
Transaksi terjadi hari H (window: 23.31 H-1 s/d 23.30 H)  → Switching kirim file CSV ke SFTP pada H+1 jam 06.00  → Engine existing proses matching otomatis  → Hasil muncul di Dashboard Rekonsiliasi (interface baru)  → Ops review: flagging unmatch, input dispute  → Jika engine bermasalah: Ops trigger re-run matching  → Management approve hasil rekon  → Finance export & proses settlement  → SLA: dana merchant terkirim sebelum H+1 jam 15.00  → Window kerja efektif Ops + Finance: ±9 jam
Batasan Scope
Fokus: membangun interface untuk Ops — bukan modifikasi engine matching
Engine SFTP ingestion, CSV parser, dan matching logic: tidak disentuh
Approval settlement: modifikasi fitur existing agar bisa handle request dari flow rekonsiliasi ini
Telegram alert proses lambat (>3 menit): mandatory
Tidak ada custom feature di luar yang didefinisikan di CR

Bab 3 — Rencana Detail Pengerjaan
A. Modifikasi Fitur Existing
A1 — User Permission System
Tambah modul baru "Reconcile" ke dalam sistem permission existing (per user, per aksi granular).
Permission
Deskripsi
Read
Bisa melihat dashboard dan semua tabel rekonsiliasi
Flagging
Bisa melakukan On-Hold / Release pada transaksi Unmatch
Input Dispute
Bisa menginput dan mengedit data dispute
Export
Bisa export CSV hasil rekonsiliasi dengan filter bank
Approve Settlement
Bisa melakukan approval hasil rekon sebelum settlement
Re-run Reconcile
Bisa trigger ulang proses matching untuk sesi hari ini
View Log Activity
Bisa melihat log aktivitas sistem dan user
A2 — Approval Settlement (Existing)
Fitur approval sudah ada. Yang perlu dilakukan: pastikan fitur ini bisa menerima dan memproses approval request dari flow rekonsiliasi — menampilkan summary nominal yang akan di-settle dan mencatat audit trail approval per sesi rekonsiliasi.
B. Fitur & Halaman Baru
B1 — Reconcile Dashboard
Halaman utama kerja harian tim Ops. Menampilkan hasil engine existing dalam interface yang bisa dioperasikan langsung.
Summary Section
Cards overview yang selalu terlihat di atas halaman: total transaksi, total match, total unmatch, total on-hold, total dispute, nominal settlement. Default: data H+1 hari ini (transaksi kemarin). Mengikuti filter tanggal jika filter aktif.
Filter Global
Tersedia di atas tabel — berlaku untuk semua tab: tanggal, switching (Rintis, Artajasa, Jalin, Alto), tipe (Acquirer/Issuer), RC, status rekonsiliasi, status flagging, dispute.
Tab Acquirer
Sub-fitur
Deskripsi
Match Table
Read-only. Kolom utama: Transaction ID, Reference Number, Tanggal & Waktu, Nominal, Merchant ID & Name, RC, Switching
Unmatch Table
Kolom tambahan: Label (Paydia-Only / Switching-Only), Flagging Status. Baris yang belum di-flag bisa di-flag oleh user dengan permission Flagging
Flagging Control
Tombol On-Hold / Release per baris di Unmatch Table. Setiap aksi tercatat di audit trail
Drill-down Detail
Klik baris manapun untuk lihat field lengkap transaksi (sesuai T2)
RC Decline Table
Read-only. Transaksi selain RC 00 dan RC 68 (detail RC dikonfirmasi via T6). Hanya untuk analisis — tidak ada aksi yang bisa dilakukan
Tab Issuer
Struktur identik dengan Tab Acquirer — Match Table, Unmatch Table, Flagging Control, Drill-down, RC Decline Table. Data source dari engine Issuer.
Tab Dispute
Sub-fitur
Deskripsi
Dispute List
Tabel semua data dispute yang diinput, terhubung ke transaksi via Transaction ID / Reference Number. Hanya mencatat dan labeling transaksi dispute — follow-up action tidak handle oleh sistem. Filter: tanggal, tipe dispute, status, switching
Form Input Dispute
Input data dispute baru secara manual — menggantikan Sharepoint
Edit Dispute
Edit data dispute yang sudah diinput selama belum di-approve
B2 — Progress Indicator
Loading indicator standar yang tampil saat engine sedang memproses. User tahu sistem berjalan tanpa perlu refresh manual.
B3 — Re-run Mechanism
Tombol "Re-run" di dashboard untuk trigger ulang proses matching jika hasil bermasalah atau engine gagal di tengah jalan. Konteks selalu sesi rekonsiliasi hari ini — tidak bisa digunakan untuk tanggal historis. Yang di-trigger ulang adalah proses matching saja, bukan load ulang file dari SFTP. Setiap re-run dicatat di audit trail: siapa yang trigger, kapan, hasilnya apa. Hanya bisa diakses oleh user dengan permission Re-run Reconcile.
B4 — Approval Flow (Reconcile)
Sub-fitur
Deskripsi
Approval Button
Hanya muncul dan bisa diklik oleh user dengan permission Approve Settlement
Confirmation Dialog
Tampilkan summary sebelum approve: total match, total unmatch yang di-release, total nominal yang akan di-settle
Audit Trail
Dicatat: siapa yang approve, kapan, summary nominal yang diapprove
B5 — Export & Filter per Bank
Sub-fitur
Deskripsi
Export CSV
Export data rekonsiliasi sesuai filter aktif. Jika filter Bank A aktif, export hanya menghasilkan data Bank A
Disclaimer Otomatis
Setiap file export menyertakan: Generated By, Date Generated, Time Generated, dan narasi disclaimer standar
B6 — Log Activity
Mencatat semua aktivitas sistem dan user: export, flagging, release, approval, input dispute, edit dispute, re-run — dengan timestamp dan nama user. Bisa diakses oleh user dengan permission View Log Activity.
